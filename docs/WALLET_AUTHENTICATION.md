# Solace Platform - Cryptographic Wallet-Only Authentication Specification

## 1. System Overview

The **Solace Platform** enforces a zero-password, wallet-only authentication paradigm across the entire application. All participants—both ordinary smart contract developers and authorized system administrators—authenticate exclusively through cryptographic signatures signed by their non-custodial Stellar / Soroban wallets (Freighter).

```
                      SOLACE WALLET-ONLY AUTHENTICATION FLOW
                      
 [Browser / User]                    [Solace Server]                  [Database]
        |                                   |                             |
 1. Connect Wallet                          |                             |
        |---- POST /api/auth/challenge ---->|                             |
        |     { address, action: login }    |-- Generate 256-bit Nonce -->|
        |                                   |-- Save Unconsumed Challenge->|
        |<--- Return Challenge Object ------|                             |
        |     { id, message, nonce, exp }   |                             |
 2. Sign Challenge in Freighter             |                             |
    (Zero key exposure, Ed25519)            |                             |
        |                                   |                             |
        |---- POST /api/auth/verify ------->|                             |
        |     { challengeId, signature,     |-- 1. Verify Expiration ---->|
        |       address }                   |-- 2. Check Replay / Nonce ->|
        |                                   |-- 3. Ed25519 Crypto Verify -|
        |                                   |-- 4. Invalidate Challenge ->|
        |                                   |-- 5. Query / Create User -->|
        |                                   |-- 6. Issue JWT & Session -->|
        |<--- Set-Cookie (HTTP-Only) -------|                             |
        |     { token, user: { role } }     |                             |
        |                                   |                             |
 3. Redirect (Dashboard or Admin)           |                             |
```

## 2. Cryptographic Challenge Specification

Challenges are ephemeral, single-use, time-limited cryptographic payloads generated by `challengeService.js`.

### Challenge Schema:
```json
{
  "id": "chal_6893ad24efbc09a128e4",
  "wallet_address": "GBWSB2OVP5JIWGJND5C46TAIM7AQH5YJ56576CGOPG3AXAFNHO7FDYPI",
  "nonce": "a78ef403b901cd...64-char-hex",
  "domain": "solace.stellar",
  "action": "solace-login",
  "issued_at": "2026-10-24T18:30:00.000Z",
  "expires_at": "2026-10-24T18:35:00.000Z",
  "used": false
}
```

### Challenge Text Representation:
To eliminate false-positive phishing warnings by third-party security scanners (such as Blockaid) while retaining full cryptographic integrity, the challenge avoids raw URL schemes (`http://` or `https://`):
```text
Solace Security Protocol Authentication

By signing this cryptographic verification challenge, you prove ownership of your Stellar wallet address without exposing private keys.

Domain: solace.stellar
Wallet: GBWSB2OVP5JIWGJND5C46TAIM7AQH5YJ56576CGOPG3AXAFNHO7FDYPI
Action: solace-login
Nonce: a78ef403b901cd8f7236a9b4d1c5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3
Issued: 2026-10-24T18:30:00.000Z
Expires: 2026-10-24T18:35:00.000Z
Network: Stellar Testnet (Protocol 22)
```

## 3. Cryptographic Signature Verification

Verification is performed entirely on the backend in `server/src/services/challengeService.js` using `@stellar/stellar-sdk`:

```javascript
import { Keypair } from '@stellar/stellar-sdk';

const keypair = Keypair.fromPublicKey(walletAddress);
const isValid = keypair.verify(Buffer.from(challenge.message, 'utf8'), signatureBuffer);
```

### Seven-Tier Security Checks:
1. **Challenge Existence**: Challenge must exist in the database.
2. **Replay Prevention**: `challenge.used` must be `false`. Reused challenges are rejected immediately.
3. **Expiration**: Current timestamp must be less than `challenge.expires_at` (5-minute TTL).
4. **Domain Match**: Challenge domain must match application domain configuration.
5. **Action Binding**: Challenge action must match intended flow (`solace-login` vs `solace-admin-login`).
6. **Address Match**: Challenge recipient address must exactly match the signing address.
7. **Ed25519 Cryptographic Verification**: Signature is validated against the Stellar public key.

Upon verification, the challenge record is immediately updated to `used = true` to prevent any possibility of replay attacks.

## 4. Database Schema (Neon PostgreSQL & Local Store)

### 1. `users` Table
```sql
CREATE TABLE IF NOT EXISTS users (
    id VARCHAR(64) PRIMARY KEY,
    wallet_address VARCHAR(56) UNIQUE NOT NULL,
    role VARCHAR(32) NOT NULL DEFAULT 'user', -- 'user' | 'admin' | 'super_admin'
    status VARCHAR(32) NOT NULL DEFAULT 'active', -- 'active' | 'suspended' | 'pending'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    last_login_at TIMESTAMP WITH TIME ZONE
);
CREATE INDEX IF NOT EXISTS idx_users_wallet ON users(wallet_address);
CREATE INDEX IF NOT EXISTS idx_users_role ON users(role);
```

### 2. `wallet_associations` Table
```sql
CREATE TABLE IF NOT EXISTS wallet_associations (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) REFERENCES users(id) ON DELETE CASCADE,
    wallet_address VARCHAR(56) NOT NULL,
    network VARCHAR(32) DEFAULT 'testnet',
    is_primary BOOLEAN DEFAULT TRUE,
    verified_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    UNIQUE(user_id, wallet_address)
);
```

### 3. `auth_challenges` Table
```sql
CREATE TABLE IF NOT EXISTS auth_challenges (
    id VARCHAR(64) PRIMARY KEY,
    wallet_address VARCHAR(56) NOT NULL,
    nonce VARCHAR(64) NOT NULL,
    domain VARCHAR(128) NOT NULL,
    action VARCHAR(64) NOT NULL,
    message TEXT NOT NULL,
    issued_at TIMESTAMP WITH TIME ZONE NOT NULL,
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    used BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_challenges_wallet ON auth_challenges(wallet_address);
CREATE INDEX IF NOT EXISTS idx_challenges_exp ON auth_challenges(expires_at);
```

### 4. `sessions` Table
```sql
CREATE TABLE IF NOT EXISTS sessions (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) REFERENCES users(id) ON DELETE CASCADE,
    wallet_address VARCHAR(56) NOT NULL,
    token_hash VARCHAR(64) NOT NULL,
    role VARCHAR(32) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    revoked BOOLEAN DEFAULT FALSE
);
CREATE INDEX IF NOT EXISTS idx_sessions_token_hash ON sessions(token_hash);
CREATE INDEX IF NOT EXISTS idx_sessions_wallet ON sessions(wallet_address);
```

### 5. `audit_logs` Table
```sql
CREATE TABLE IF NOT EXISTS audit_logs (
    id VARCHAR(64) PRIMARY KEY,
    actor_wallet VARCHAR(56) NOT NULL,
    action VARCHAR(64) NOT NULL,
    target VARCHAR(128),
    details JSONB,
    ip_address VARCHAR(64),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_audit_actor ON audit_logs(actor_wallet);
CREATE INDEX IF NOT EXISTS idx_audit_created ON audit_logs(created_at);
```

## 5. Soroban & XML Audit-Credit Integration

The platform enforces credit-based smart contract audits:
- **Starter Package**: 30 XML for 3 Audits (10 XML/audit)
- **Professional Package**: 60 XML for 6 Audits (10 XML/audit)
- **Enterprise Package**: 90 XML for 9 Audits (10 XML/audit)

### Payment & Verification Rules:
1. All audit credits are tied directly to the user's verified wallet address in `credit_balances`.
2. Blockchain transactions on Stellar Testnet are reconciled via Horizon RPC.
3. Administrative adjustments via `/api/admin/credits/adjust` require an authorized admin session and record the reason in the audit log.
4. No audit can be initiated without a verified server-side credit deduction.
